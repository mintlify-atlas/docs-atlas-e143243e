Tau loads two kinds of reusable Markdown from disk: **skills** and **prompt templates**. Skills teach the model *how* to do a task — they are injected into the system prompt as reference knowledge the model can pull in when relevant. Prompt templates are saved prompts you trigger by name, with optional fill-in variables. Both can live at the user level (available in every project) or inside a specific project directory.

## Where the Files Go

Skills and prompt templates each have four discovery locations, loaded in increasing precedence — a later location overrides an earlier one when names clash:

<Tabs>
  <Tab title="Skills">
    ```text
    ~/.tau/skills/          # lowest precedence
    ~/.agents/skills/
    <cwd>/.tau/skills/
    <cwd>/.agents/skills/   # highest precedence
    ```

    Each skill is a **directory** containing a `SKILL.md` file. The directory name is the skill name.
  </Tab>
  <Tab title="Prompt Templates">
    ```text
    ~/.tau/prompts/          # lowest precedence
    ~/.agents/prompts/
    <cwd>/.tau/prompts/
    <cwd>/.agents/prompts/   # highest precedence
    ```

    Each template is a single `.md` file. The filename (without extension) is the invocation name.
  </Tab>
</Tabs>

After adding or editing files while the TUI is open, run **`/reload`** to rediscover them. Tau reports duplicate or overridden resources as diagnostics (not fatal errors) and shows a red transcript alert at startup when the same name appears in multiple locations — it lists both paths so you can rename or remove the unintended duplicate.

## Skills

A skill follows the [Agent Skills specification](https://agentskills.io/specification#directory-structure): a directory named after the skill, containing a `SKILL.md` file. Optional frontmatter gives it a description:

```text
~/.tau/skills/security-review/SKILL.md
```

```markdown
---
description: Review a diff for security issues.
---

Steps to review the current diff for security problems:

1. Check for hardcoded credentials or secrets
2. Review authentication and authorization boundaries
3. Look for injection vulnerabilities in user-supplied input
...
```

Supporting files — references, code snippets, checklists — can live alongside `SKILL.md` inside the same directory.

<Warning>
Bare `.md` files at the root of a skills directory (e.g. `~/.tau/skills/review.md`) are **not** loaded as skills. Tau surfaces a diagnostic instructing you to move them:

```bash
cd ~/.tau/skills
mkdir review && mv review.md review/SKILL.md
```
</Warning>

Tau places each skill's **name**, **description**, and **path** in the system prompt — not the full content. The model reads the full `SKILL.md` (via the `read` tool) when its description matches the task at hand.

### Invoking a Skill

Run `/skills` in the TUI to open a searchable picker of all loaded skills. Select one to insert its invocation into the prompt. From the picker:
- **Enter** — inserts `/skill:name` into the prompt for further instructions
- **F1** — shows the complete frontmatter description
- **Ctrl+Enter** — displays the full `SKILL.md` in the transcript for inspection without adding it to model context

Or invoke a skill explicitly in the prompt:

```text
/skill:security-review check the changes on this branch
```

For longer instructions, put the request on following lines:

```text
/skill:security-review

Check the changes on this branch.
Pay special attention to authentication boundaries.
```

`/skill:<name>` is a *prompt-expansion* path — Tau expands the skill and any inline or multiline request into your prompt, then runs it as a normal turn.

### Hiding a Skill from the Model

Set `disable-model-invocation: true` in frontmatter to keep a skill out of the system prompt entirely. The model won't see it or invoke it on its own, but you can still use it with `/skill:<name>` and it still appears in the `/skills` picker:

```markdown
---
description: Generate the weekly status report.
disable-model-invocation: true
---

Steps to build the report...
```

This is useful for user-triggered workflows that would add noise to the skill list or tempt the model to fire them at the wrong time.

## Prompt Templates

A prompt template is a saved prompt in a single `.md` file, invoked by its filename. For example, `~/.agents/prompts/wt.md` is invoked with `/wt`.

```markdown
---
description: Implement a feature in an isolated git worktree.
---

Implement this feature safely in a new worktree:
{{ feature }}
```

If a template has `{{ variable }}` placeholders, variables are filled from the arguments you pass after the invocation: `/wt add caching`. If a template has **no** placeholders, your arguments are appended after a blank line.

### Discovering and Using Templates

Run **`/prompts`** in the TUI to open a searchable picker of all loaded templates:
- **Enter** — inserts the invocation (e.g. `/wt`) into the prompt without submitting
- **Ctrl+E** — opens the template's Markdown for editing directly in the TUI
- **Ctrl+S** (in the editor) — saves the file; Tau reloads resources automatically

<Note>
The filenames `prompts.md` and `skills.md` are reserved for the built-in `/prompts` and `/skills` picker commands. Tau ignores templates with those names and reports a resource diagnostic. Rename the file to load it as a custom template.
</Note>

## Skills vs. Prompt Templates

<CardGroup cols={2}>
  <Card title="Use a Skill when…" icon="brain">
    You want to give the model **reference know-how** it can pull in autonomously when a task calls for it. Invoked explicitly with `/skill:name` or automatically when the model recognizes relevance.
  </Card>
  <Card title="Use a Prompt Template when…" icon="keyboard">
    You keep typing the **same instructions** and just want a shortcut, optionally with fill-in variables. Invoked by name (e.g. `/wt`) and never injected into the system prompt automatically.
  </Card>
</CardGroup>

<Tip>
Keep personal, cross-project helpers in `~/.agents/` so they follow you everywhere. Keep project-specific ones in the repo's `.tau/` or `.agents/` so collaborators share them — subject to project trust approval.
</Tip>

## Writing an Effective Skill

A well-written skill file focuses on **how** to accomplish a task, not on what the task is. Structure it as a step-by-step procedure the model can follow:

```markdown
---
description: Perform a thorough code review of a pull request diff.
---

When reviewing a pull request:

1. Read the PR description and understand the stated intent
2. Check that the implementation matches the stated intent
3. Look for edge cases not covered by the changes
4. Verify test coverage for new behavior
5. Check for breaking changes to public APIs
6. Flag any security concerns (auth, injection, secrets)

Format feedback as inline comments with file:line references where possible.
```

Keep skills focused on a single domain. Create multiple skills rather than one large catch-all — the model reads the full file only when the description matches, so precision in the description matters more than completeness.
